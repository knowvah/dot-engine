# C 版 Graphviz との既知の差異 {#known-divergences-from-c-graphviz}

@knowvah/dot-engine は、正規の C 実装にできる限り忠実であることを目指しています。
C のソースが仕様であり、一覧にない差異は、受け入れられた挙動ではなく
欠陥として扱われます。

> **ここでの「一致」の意味。** コーパスのパリティ判定 `conformant` は
> **厳密な決定的許容誤差**であり、SVG のバイト単位の完全一致では*ありません*。
> 数値の座標とパスは **±0.01** の範囲内で一致し、非数値の内容（タグ、色、テキスト）は
> 完全に等しくなければなりません
> (`compareSvg(…, 'deterministic')`)。この文書全体を通して、「一致」と
> 「適合」はその許容誤差による判定を指します。完全な定義：
> [適合性](./conformance.md)。

出力が*実際に*異なる場合、その差異は次の 3 つのクラスのいずれか 1 つに正確に分類されます。

1. **受け入れ済みの差分** — 調査し、根本原因まで理解したうえで、
   **意図的に適合させないことを選んだ**差異。それぞれ、以下で範囲が限定され、
   特徴づけられ、正当化されています。これらはバグではなく、個別に範囲を定めた
   具体的な理由がない限り「修正」されることはありません。
2. **追跡中のロングテール** — 今後*解消される*既知のギャップで、それぞれオラクルで固定された
   修正方針があります。最新の件数は
   [`test/corpus/PARITY-dot.md`](https://github.com/knowvah/dot-engine/blob/main/test/corpus/PARITY-dot.md)
   にあります。
3. **非目標** — 意図的なスコープの境界（再現しようと最初から考えていない形式やメカニズム）。

継続的に更新される権威ある記録は、
[`PARITY-dot.md`](https://github.com/knowvah/dot-engine/blob/main/test/corpus/PARITY-dot.md)
（ネイティブの `dot` に対する入力ごとのパリティダッシュボード）と、
[`plans/port-catalog/README.md`](https://github.com/knowvah/dot-engine/blob/main/plans/port-catalog/README.md)
（アルゴリズム単位の移植状況の一覧）です。

どのグラフが*受け入れ済み*（後述のクラス 1）かについての**機械可読な**唯一の情報源は
[`test/corpus/accepted-divergences.json`](https://github.com/knowvah/dot-engine/blob/main/test/corpus/accepted-divergences.json)
です。ツールはレポート作成時にこれを結合します。`PARITY-dot.md` は**受け入れ済みの差分**を
**追跡中**のバックログから分離し、ルールゲートはその許可リストをここから取得します。
以下の本文の各節は各エントリーを説明しています（A1 と A3 は現役、A2 はクローズ済みで
履歴として残されています）。CI テスト (`accepted-divergences.test.ts`) が、
受け入れ済みのすべてのグラフが依然として差異を示すことを強制するため、
この一覧が気づかないうちに陳腐化することはありません。

## 受け入れ済みの差分（意図的に適合させないもの） {#accepted-deltas-we-deliberately-do-not-make-conformant}

バイト単位の一致を追い求めずに差分を受け入れるのは、次の条件が**すべて**成り立つ場合に限ります。

- 根本原因が**移植性の制約**（JavaScript／ブラウザーのランタイムが正確に再現できないもの）であり、
  ポートのロジックの誤りではない。
- 差異が**知覚できない程度**であり、証明可能な形で**有界**である。
- 修正の**コストと影響範囲が、見返りに対して不釣り合い**である（典型的には、すでに適合している
  数百のグラフが使う共有プリミティブに触れることになり、1 ピクセルの何分の 1 かの改善のために
  リグレッションの危険を冒すことになる）。

差分を受け入れる際には、利用者が驚かないよう、ここでその特性を記述します。
受け入れ済みの差分の影響を受けるグラフは、バイト単位の基準ではなく、**構造／許容誤差**の基準で
検証されます。

### A1. 浮動小数点の決定性（力指向エンジン） {#a1-floating-point-determinism-force-directed-engines}

**影響を受けるもの：** `neato`、`fdp`、`sfdp`、`circo`、`twopi`、`osage`（反復型の
ばねモデルエンジン）。`dot` エンジンの*レイアウト*は、この反復モデルの決定性の影響を**受けません**。
`dot` のスプラインルーティングにおける、別個の、狭い範囲に限定された浮動小数点の差分については
後述の **A3** で扱います。

> **スコープ。以前は未測定の注意書きだったが、現在は部分的に測定済み。**
> **dot エンジンのメイン SVG 調査** (`test/corpus/survey.ts`) は依然として
> **dot のみ**です。ネイティブオラクルは `GVBINDIR=/tmp/ghl` の下で動作し、これは
> `core` と `dot_layout` のプラグイン**のみ**をシンボリックリンクします
> （`test/corpus/gen-headless-gvbindir.sh` はちょうど `core dot_layout` をループします
> — `neato`/`fdp`/`circo`/`twopi`/`osage`/`sfdp` のレイアウトプラグインは存在しません）。
> そのうえ、オラクルもポートも `dot` エンジンで呼び出されます。したがって、
> `*_neato` / `*_circo` / `root_twopi` のようなコーパス ID は、その調査では本来のエンジンではなく
> `dot` でレイアウトされた*ファイル名*にすぎず、A1 はそこでは**ゼロ個**のグラフにしか
> 一致しません — それはエンジンが適合していると証明されたからではなく、その調査が
> それらを一度も実行しないからです。
>
> **しかし、A1 の 6 つのエンジンすべてに、専用のネイティブエンジン調査が用意されました。**
> `test/corpus/engine-walk.ts` と `parity-report.ts` によるもので（`GVBINDIR` に依存せず —
> それぞれが `dot -K <engine> -Txdot` を直接起動します）、厳密さの異なる 2 つのレベルで、
> 以下に別々に記述されています。`circo`/`twopi`/`osage` は dot 調査と同じ
> **±0.01 の決定的**許容誤差で実行され、ID ごとに根本原因を分類します
> （後述の「エンジントラックの受け入れ」）。`neato`/`fdp`/`sfdp` は、より緩い
> **±0.5 の特性評価**許容誤差で実行され、ID ごとの分類はまだありません
> （後述の「反復型エンジンの特性評価」）。現在のエンジン横断の数値：
> [`PARITY.md`](https://github.com/knowvah/dot-engine/blob/main/test/corpus/PARITY.md)。

**特性。** これらのエンジンは反復的な数値レイアウトを実行し、その結果は浮動小数点の丸めに依存します。
具体的には、融合積和演算 (FMA) と `Math.pow` で、JavaScript エンジンや CPU アーキテクチャによって
異なりえます。ポートは可能な限り C の演算順序に合わせています（`src/common/fma.ts`、
`src/common/arm-pow.ts`）。たとえば `sfdp` は、PRNG と `fma` を一致させることでネイティブオラクルに対して
有効数字約 6 桁に固定されます。しかし、座標まで完全に同一の再現は**プラットフォームをまたいでは保証されません**。
トポロジーは保たれ、潜在的な差異は細かいノード座標にあります。

**受け入れる理由。** これは JS で動作することに伴う厳しい制約であり、設計上の選択ではありません
— A3 の Apple `hypot` に対する感度と同じ系統のものです。対象とするすべてのランタイムで
超越関数／FMA の結果がビット単位で同一になることを保証する方法はないため、バイト単位の基準は
単にコストが高いのではなく、検証不可能です。A1 を（単に注意書きとして添えるのではなく）**評価する**ためには、
別個のネイティブエンジンのパリティトラックが必要でした。これは 2026-07-11 に
`test/corpus/engine-walk.ts` と `parity-report.ts` として構築され、各入力を `dot` ではなく
それ自身のエンジンで調査します。この作業の誠実な上限は、A1 を「参照プラットフォームでは
現役の差異なし」まで**狭める**ことであり、プラットフォーム間の注意書きを取り除くことでは決してありません。
これまでの結果（後述）はその上限を守っています。`circo`/`twopi`/`osage` は、それぞれ
少数の本物の A1/A9 の事例を発見して根本原因を特定しました。また `neato`/`fdp`/`sfdp` は
910 件の母集団でネイティブの 0.5pt 以内にそれぞれ 90.8/77.5/68.0% が入っており、
これは移植された演算（`fma.ts`、`arm-pow.ts`、一致させた PRNG）がほとんどのグラフで
成り立っていることを意味します。そして残るすべての diverged ID は、未分類のずれとして放置されるのではなく、
（ソルバーのずれかポートの欠陥かを）注入によって個別に原因が特定されています。
後述の反復型エンジンの特性評価を参照してください。

**エンジントラックの受け入れ：twopi の矢印ファミリー。** <a id="a1-twopi-arrows-family"></a>
上のブロック引用は、A1 が 0 個のグラフにしか一致しない dot エンジンの SVG 調査を説明しています。
一方、別個の `twopi` の **xdot エンジントラック**（`parity-twopi.json`、ネイティブの
`dot -K twopi -Txdot` オラクル、`test/corpus/engine-walk.ts`）は、本来のエンジンで*実際に*実行され、
9 個のコーパス ID で具体的に検証された A1 の事例を示します。
`graphs-arrows`、`graphs-newarrows`、`graphs-arrowsize`、`linux.x86-arrows_dot`、
`macosx-arrows_dot`、`nshare-arrows_dot`、`share-newarrows`、`windows-newarrows`、
そして（2026-07-28 に追加、905 件の母集団に新規に加わった）directed/ の兄弟である
`tree-graphs-directed-oldarrows` です。いずれも支配的な 1 本のエッジ
（`Z->I` または `i->Z`。描画オペレーションの差分は 12〜64 個）で乖離しています。
注入 A/B（意思決定ジャーナル、2026-07-10 の「injection A/B verdicts:
twopi arrows family EXONERATED...」エントリー）がメカニズムを直接証明しました。
ネイティブの `spline_edges` の入口の `ND_pos` をダンプし、それをポートの
`splineEdgesShifted` に注入すると、`graphs-arrows` で**完全に適合する**出力が得られます
（`Z->I` はオラクルとバイト単位で同一になり、同じ 7/14 点のスプラインになります）。
したがってこの差異は 100% が、`twopi` の PRISM オーバーラップ除去ソルバーに由来する
ルーティング前のノード位置のずれであり、ポートのスプラインルーティング／出力は
潔白です。8 個の ID のうち 6 個で見える症状は、ベジェの点数の反転
（`unfilled_bezier[ptCount]: 8 vs 14`）です。`Proutespline` が当てはめるピース数は、
ずれたノード位置が障害物の境界のどちら側に落ちるかに敏感なため、PRISM の反復解法の下流での
サブ ULP の位置の違いが、当てはめられたスプラインのセグメント数を反転させます
（残りの 2 個の ID、`graphs-arrowsize`/`nshare-arrows_dot` は、ピース数の反転を伴わない、
位置のみのより小さな差として同じずれを示します）。エンジントラックのレベルでは
`test/corpus/accepted-divergences-engines.json` により受け入れられ、
`parity-report.ts` によって `PARITY-twopi.md` に結合されます — dot トラックの
`PARITY-dot.md` に対して `accepted.ts` が行うのと同じ結合です。

`oldarrows` の根本原因分析 (RCA)（2026-07-28）により、このファミリーの点数の症状が反転する
正確な箇所が特定されました。その `i`–`Z`–`I` のファンは円環の直径上で一直線に並んでおり、
pathplan の `directVis` の `intersect()` は、障害物の頂点が線分の「上」にあるとき視線を遮ります。
そこで `wind()` の 1e-4 の共線性の許容誤差により、線分から 270pt 離れたノードですら
共線と見なされ、（共線を仮定する）`inBetween()` は **x 射影のみ**の判定に退化します。
つまり、頂点の x が 2 つの端点の x 座標の間にある ULP 幅の区間の厳密な内側に入るとき、
かつそのときに限り、その頂点は視線を遮ります。したがって、鏡像になった 2 本の放射状エッジの
どちらが曲がるかは、PRISM の解から得られる、名目上等しい 3 つの x 値の最下位 ULP の順序に
かかっています — C は `Z->I` を曲げ（ノード `i` の軸上の頂点が自分の区間の内側に入る）、
ポートは `i->Z` を曲げます（ノード `I` の頂点が自分の区間の内側に入る）。それぞれの側で
ダンプした障害物の集合に対して `directVis` をオフラインで再現すると、各側の判断が
正確に再現され、オラクルのルーティング前の `ND_pos` をポートに注入すると差分は 0 になります
（`attribution-twopi.json`）— ルーティングと出力はバイト単位で忠実です。

`1855` は、同じルーティング前の PRISM の浮動小数点メカニズムの、放射状／スター**鏡像**の
バリアントです（2026-07-11 に受け入れ）。その 31 枚の葉はちょうど同一円周上にあるため、
スターレイアウトは反転対称であり、PRISM のオーバーラップ除去は対称性に不安定な平衡点に位置します。
`circleLayout` の `setAbsolutePos` における 5 枚の葉の角度での、V8 と libm の `cos`/`sin` の
1 ULP の違いが反対側の鏡像の盆地を選び、放射状レイアウト全体が、オラクルのものとちょうど x 軸について
鏡像になって着地します（ノードの最大変位 6.04pt、bb は保存）。注入 A/B は
両方向を証明しました。C の正確な `circleLayout` の位置をポートの PRISM に与えると、
オラクルをノードごとに再現し (3e-14)、ULP が異なる 5 枚の葉の位置だけを元に戻すと、
レイアウト全体がポートの鏡像に戻ります。完全な RCA：`.agent-notes/twopi-radial-drift-rca.md`
（意思決定ジャーナル 2026-07-11）。

**反復型エンジンの特性評価：neato/fdp/sfdp。** <a id="a1-iterative-characterization"></a>
上の `circo`/`twopi`/`osage` のエンジントラックとは異なり、`neato`/`fdp`/`sfdp` は
ID ごとの分類が**まだ行われていません**。`engine-walk.ts` はこの 3 つについて
`tolerance: 0.5` フィールドを記録し、`parity-report.ts` はそれらを
[`PARITY.md`](https://github.com/knowvah/dot-engine/blob/main/test/corpus/PARITY.md)
の別の「Iterative engines (±0.5 characterization)」セクションに表示します。これは
この文書の他の箇所の ±0.01 の決定的な合格率とは、明示的に**比較できません**。
現在の件数（910 件の母集団。合格率は、[適合性](./conformance.md)に従い、
C のオラクルがレンダリングできない入力を除く）：

| エンジン | 調査数 | ±0.5pt 以内 | 非適合（すべて原因特定済み・受け入れ済み） | ポートエラー / タイムアウト | オラクルエラー |
|---|---:|---:|---:|---:|---:|
| `neato` | 910 | 826 (90.8%) | 83 | 1 | 0 |
| `fdp`   | 910 | 703 (77.5%) | 204 | 0 | 3 |
| `sfdp`  | 910 | 619 (68.0%) | 290 | 1 | 0 |

（2026-07-11、762 件での最初のスイープでは、±0.5pt 以内は 263/311/260 でした —
現在の率への跳ね上がりは、その後に入った ID ごとの修正によるもので、主なものは
neato の未移植だった `user_pos`/`P_SET` の処理、エンジン初期化の統合、
そして `setEdgeType` のマクロと関数の修正です。）

最初のスイープの時点と違い、diverged のすべての行が個別に原因特定されています。
注入ハーネス (`test/corpus/attribute-divergence.ts`) が、ネイティブオラクルの
ルーティング前の `ND_pos` をポートに与えて再比較します。現在の diverged な ID はいずれも、
`drift-exonerated`（ソルバーのずれを取り除けば、ポートのルーティングと出力がオラクルを
正確に再現する）か、個別に受け入れられた少数の ID ごとの残差のいずれかです
（3 つのエンジンすべてでの `241_0` の CDT の内接円の同順位、neato の `2239`、
sfdp の `42`/`2556`）。後述のクラスの受け入れは、この潔白とされた集合を正式化するものです。
最新の件数はエンジン別のダッシュボードにあります
([`PARITY-neato.md`](https://github.com/knowvah/dot-engine/blob/main/test/corpus/PARITY-neato.md)、
[`PARITY-fdp.md`](https://github.com/knowvah/dot-engine/blob/main/test/corpus/PARITY-fdp.md)、
[`PARITY-sfdp.md`](https://github.com/knowvah/dot-engine/blob/main/test/corpus/PARITY-sfdp.md))。

**A1-drift クラスの受け入れ（反復型エンジン、メンバーシップは算出）。**
<a id="a1-drift-iterative-engines"></a> `test/corpus/accepted-divergences-engines.json` は、
反復型エンジン（`neato`、`fdp`、`sfdp`）ごとに 1 つの `"A1-drift"` **クラス**エントリー
— `{ class: true, attributionFile, ref }` — を持ちます。これは、上の
`circo`/`twopi`/`osage` トラックで使われる ID ごとのエントリーとは別物です
（D2、`plans/iterative-parity-campaign/decisions.md`）。ID ごとのエントリーと異なり、
クラスのメンバーシップがレジストリに手作業で列挙されることはありません。`parity-report.ts` が
レポート作成時に、対応する `attribution-<engine>.json`
（T1 の注入による原因特定ハーネス、`test/corpus/attribute-divergence.ts`）から算出します
— ネイティブのルーティング前の `ND_pos` をポートに注入して再比較し、±0.5 で適合した
diverged な ID はすべて、そのファイルで `verdict: 'drift-exonerated'` を得ます。これは、
2 つのエンジンの反復ソルバーが、数値的には異なるものの、それぞれ内部的に整合したレイアウトに
収束したこと（上記の A1 の特性評価のとおり浮動小数点の累積の違いであり、ポートの
ルーティングや出力のバグではない）を意味します。ID ごとの証拠 — バケットの形、
ベースと注入後の差分数、一様な平行移動／鏡像の検出 — は原因特定の成果物自体にあり、
この文書やレジストリには重複して記載されません (D2)。その後に完全に合格するようになった ID や、
再度の原因特定で判定が変わった ID は、次回のレポート再生成で自動的にクラスから外れます
— 古くなった受け入れを編集する必要も、ガードテストの失敗もありません。
`attribution-<engine>.json` がまだ生成されていないエンジンでは、クラスは
「attribution pending」（原因特定待ち）としてメンバーゼロで表示され、受け入れがまったくない場合と
同じになります — クラスのエントリーはそのデータより先に存在してよいのです
（`test/corpus/accepted-divergences-engines.test.ts` を参照）。

### A2. テキスト計測（フォントメトリクス）→ ラベル主導のレイアウト — クローズ済み <a id="a2-text-measurement-font-metrics-→-label-driven-layout-—-closed"></a> {#a2-text-measurement-font-metrics-label-driven-layout}

**ステータス（2026-07-01）：クローズ。** このクラスで受け入れられているコーパス ID は
もうありません。この節は、そのメカニズムと、それを無力化した差し替え可能な
`TextMeasurer` のシームの歴史的な記録として残されています。
一連のテキスト計測の修正（`EstimateTextMeasurer` への切り替え、フォントを考慮した

(`graphs-`/`share-`/`windows-proc3d`) のすべてで完全に **`conformant`** です。
bbox は一致し、パスデータの差分はゼロ、ラベルアンカーの差分もゼロです。

**最後のメンバーの退役（2026-07-01）。** **`NaN` ファミリー**
(`graphs-NaN` / `share-NaN` / `windows-NaN`) は、そのノードのジオメトリがすでに C と
正確に一致していた（76/76 の基準点）後も、長らくここに置かれていました。
本当の残差 — 4 組の対向する 2 サイクルのペア
（`Target↔TThread`、`Interp↔InterpF`、`Event↔Target`、
`AtomProperties↔NRAtom`）にある 8 個の直線エッジの端点が 6〜14 pt ずれていたもの — は
再診断され、**フォントメトリクスの影響ではまったくなく**、dot のマルチエッジルーティングにおける
2 つのポートの欠陥であることが判明しました
（ミッション `plans/fix-nan-a2-retire/`、
`.agent-notes/nan-edge-endpoint-diagnosis.md`）。

1. **対向ペアのレーン順序。** ポートは、Multisep のレーンオフセットを割り当てる前に、
   平行エッジの各グループを元の作成順 seq で並べ替え直していました。C は
   edgecmp が収集した順序でレーンを割り当てます（MAINGRAPH の順方向の代表が最初、
   AUXGRAPH の逆向きのメンバーが 2 番目 — `dotsplines.c:419`、
   `make_regular_edge:1885-1907`）。逆向きのメンバーが先に宣言された 2 サイクルでは、
   各エッジが相手の 18 pt の回廊に描かれていました。
2. **ランクをまたぐマージされたエッジでの、偽のフラット隣接。**
   `markAdjacent` が、C の同一ランクのガード（`flat.c:272-276`）なしで
   `ND_other` のエントリーにマークを付けていたため、`groupSize` のフラット隣接による
   ショートサーキットが、portcmp のグループの区切りを飲み込んでいました。

両方を忠実に修正した結果、このファミリーは 3 つのディレクトリすべてで **`conformant`** になりました
（要素ごと：差異のあるノード 0、エッジ 0）。同じメカニズムにより、`42`、`clust2`、`ngk10_4`
（structural-match → conformant）が解決し、`b124` が diverged から structural-match に移りました
— いずれも 2 サイクル／平行ペアです。

**調査の両側が同じ推定器を実行する — 計測は無力化されている。**
ネイティブの `dot` オラクルは、ヘッドレスの `GVBINDIR`
(`test/corpus/gen-headless-gvbindir.sh` → `/tmp/ghl`) の下で動作し、これは
`core` と `dot_layout` のプラグインのみをシンボリックリンクします — `gd`/`pango`/`quartz` の
テキストレイアウトプラグインはありません。そのスロットが空だと、graphviz は組み込みの
`estimate_textspan_size` にフォールバックします。TypeScript ポートの `EstimateTextMeasurer`
(`src/common/textmeasure.ts`) は同じルーチンの忠実な移植であり、Node でのデフォルトで、
`createMeasurer()` (`src/common/textmeasure-factory.ts`) によって解決されます。
**したがって、すべてのパリティ比較の両側が、同一の推定器でテキストを計測します** —
実際の FreeType/pango のグリフ送り幅が比較に入ることはありません。ここでの判定の
リグレッションがフォントではなくレイアウトコードを指すのはこのためであり、
推定器自体のバグ（UTF-8 のバイト数の数え方、垂直メトリクスのフォント対応）を直したことが、
フォントメトリクスのギャップを単に狭めるのではなく、このクラスのほとんどを完全に解消した理由です。

**差し替え可能な `TextMeasurer` のシーム。** この無力化が可能なのは、
テキスト計測がどちらのエンジンにも直接組み込まれておらず、意図的なシームになっているからにほかなりません。
`TextMeasurer` は 1 メソッドのインターフェース (`measure(text, font, size,
flags) → {w, h, …}`) で、ラベルのサイズを決めるすべての呼び出し箇所に依存性注入されます —
`polyInit`、`recordInit`、`initEdgeLabels`、`buildNodeLabel` はそれぞれ計測器を引数として受け取り、
グローバルを通してテキストを計測するものはありません。テストや CI では
`setTextMeasurer(...)` または `GV_TEXT_MEASURER=estimate` で固定されます。
このシームにより、残差が計測のみによるものであることを*証明*することもできます。
C が計測した正確な幅（オラクルから取得したもの）をポートに与え、レイアウトが
C を正確に再現するかどうかを確認するのです。この実験こそが、`proc3d` の A2 判定を
当初裏づけたものでした（後述の歴史的付録を参照）— この手法は今も有効です。
その逆の使い方がこのクラスを退役させました。両方の調査側で計測が
証明可能な形で無力化されていたため、`NaN` のエッジの残差はフォントメトリクスの影響では
ありえず、そのことが再診断を促し、上記の 2 つのルーティングの欠陥の発見につながったのです。

### A3. スプラインルーティングにおける `hypot` の同順位解決（`dot`） {#a3-hypot-tie-break-in-spline-routing-dot}

**影響を受けるもの：** エッジルーティングの回廊が**幾何学的に対称**な `dot` のグラフ
— 典型的には、短い対称なフラットエッジの弧。観測された例：`2368` は
*structural-match* にとどまります（**1 本**のエッジ `376->76` で maxΔ ≈ 10.2 pt）。
同じ同順位解決は、回廊がちょうど鏡像対称のとき、ファンインの大きいハブに入る**長い**
（複数ランクにまたがる）エッジにも現れます。`graphs-b100` /
`graphs-b104`（同一のソース）は、`Node23730->Node23729` の 1 つの結節点で maxΔ 20
（ちょうど 1 ランク行分）だけ乖離します — すべてのノード位置と、上流のボックス／多角形／
張られたパスの構造はすべて C とバイト単位で同一で、`findMaxDev` が鏡像対称な内部点の
どちらをベジェの結節点にするかについての約 1 ULP の選択だけが異なります。
短いフラットエッジの形は `241_1`（structural-match、
maxΔ ≈ 2.4 pt）としても現れます — これは、オラクルで固定された `241_0` の乖離する兄弟で、
`241_0` では C のノイズがむしろ最初のものを残します。同じ同順位解決は、`2413_1`
（structural-match、maxΔ 67.65）と `2413_2`（T11 の swapBezier-reverse 修正が入れば maxΔ ≤99.55 —
それまでは、そのファイルで報告される maxΔ 1922.26 は、無関係で別途追跡中の欠陥に支配されています）における
ラベル付き 2 サイクルの後退エッジのスリット回廊の分割、および `graphs-decorate` における
クラスター内のラベル付きエッジ 1 本（maxΔ 43.54）も生じさせます。いずれの場合も、
2 つの候補の分割コーナーは、位置に依存する Apple の `hypot` のノイズが勝者を選ぶ前の時点で、
互いに 5.7e-13 (2413 ファミリー) / 3e-14 (decorate) 以内で同順位になっています。`2371`
（structural-match、maxΔ 16.8）は、無関係な 2 本のエッジ
（`g[9263]` `r6837mid--r9687mid`、`g[23859]` `r38mid--r8699mid`）で同じ特徴を示します。
ポートは両方でオラクルの制御点列の正確な鏡像を出力し、結節点の y は同一の Δ16.8 だけ
反転しています（上側と下側の分割比が入れ替わっている）。
その起源は、他のメンバーの CONFIRMED（確認済み）の確度ではなく **MEDIUM** の確度とされます。
`2371` は約 199 個のコンポーネントをパックしており、pathplan のローカル座標とページ座標が
切り離されるため、3 回の計装を試みても同順位を `route.ts:209` にライブで対応づけることが
できませんでした。ストレートモードのセグメント化や、クリップ後の `recover_slack` が起源である
可能性は完全には排除されていません。完全な診断：
`plans/residual-cleanup/analysis/2371-mirror.md`。ルーティングされるエッジの大半は
影響を受けません。

**特性。** スプラインフィッター（`Proutespline` → `findMaxDev`、
`src/pathplan/route.ts`）は、当てはめたベジェを、偏差が最大となる内部のルート点で分割します。
回廊が対称だと、2 つの候補の分割点は**数学的に完全な同順位**になり、勝者は、
絶対座標でのベジェ評価における約 1e-14 の浮動小数点のキャンセレーションノイズによって決まり、
その**符号は絶対位置に依存します**。

C の偏差距離は libm の `hypot` ですが、オラクルを生成した macOS の Apple `hypot` は
独自実装であり、ビット単位で一致する移植可能な `hypot` は**存在しません**（graphviz の座標域で
それに対して測定した、ビット同一率：V8 の `Math.hypot` ≈ 63%、正しく丸められる／Arm 方式の `hypot`
≈ 84%、fdlibm の `hypot` ≈ 90%、`sqrt(dx²+dy²)` ≈ 94%）。この ULP のノイズのために、
**C 自身が一貫していません**。平行移動で合同な 2 つの弧を、**反対**のコーナーに向けて分割します。

ポートは**平行移動不変**な同順位解決（真の同順位は常に最初のインデックスに解決される）を使うため、
位置にかかわらず、そのような弧の*すべて*を同じ方法で描きます — 自己整合的であり、
C のノイズも最初のものを残す弧（たとえば `256->436` や `241_0 5:ne->8:nw`）では C と一致し、
C のノイズが反対側に倒れる箇所（`376->76`）でのみ乖離します。端点、矢じりの目標、
他のエッジ、すべてのノード、ラベル、バウンディングボックスは許容誤差内で一致し、
1 本の弧の内部の制御点だけが動きます（腹で約 1〜2 pt）。

**受け入れる理由。** Apple の `hypot` は、**A1** の FMA/`pow` と同様に、JS エンジンや CPU を
またいで再現可能ではありません — これは同じ移植性の制約で、場所が `dot` のスプラインルーターに
あるだけです。C の*位置に依存する*選択に合わせるということは、C の厳密な同順位解決を
採用することを意味しますが、それはルーティングされるすべてのエッジが通る**共有プリミティブ**の
中にあります。そうすると、`376->76` の一致と引き換えに、C が逆側に着地する弧で*新たな*
不一致が生じ（`241_0` と `cnt=3` のフラットエッジのオラクルケースがリグレッションする）、
差し引きゼロで、しかもポートの平行移動不変性まで犠牲になります。そこで、一貫した
（不変な）ルーターを維持します。これは有界で、知覚できない程度の `dot` の差分であり、
未解決のバグではありません。完全な調査：
`.agent-notes/2368-residual-flat-label-ranksep.md`。

### A5. 無効な入力バイト（エンコーディングの表現） {#a5-invalid-input-bytes-encoding-representation}

**影響を受けるもの：** `1367`（diverged、maxΔ 0 — 構造上の差分がちょうど 1 つ）。

**何が異なるか。** 入力ファイルのノード名の中に、裸の UTF-8 後続バイト (`0x80`) が含まれています。
C は、裸の後続バイト 0x80–0xBF を「それ自身を表す有効な文字」として扱い
（`lib/common/utils.c:1200-1207`、警告なし）、ノード名の `<title>` テキストは
文字セット変換を完全にバイパスします（`agnameof` のバイトがそのまま `gvputs_xml` に流れます）。
したがってオラクルの SVG は生のバイトを含み、宣言されたエンコーディングにもかかわらず
**有効な UTF-8 ではありません**。ポートは、無効な UTF-8 の入力を latin1 フォールバックで
デコードし (`0x80 → U+0080`)、整形式の UTF-8 (`\xc2\x80`) を出力します。

**受け入れる理由。** ポートの I/O 境界は JS の文字列（ブラウザーライブラリ）です。
生の無効なバイトは `renderSvg` の文字列の戻り値を往復できません。C にバイト単位で
合わせることは、すべての利用者にとって出力のエンコーディングを壊すことを意味します。
latin1 フォールバックは、C 自身の「Latin-1 として扱う」回復のセマンティクス
(`utils.c:1249`) を反映しています。これはコードより下の層 — 表現層 — の制約であり、
移植を見送った移植可能な挙動ではありません。1367 のそれ以外はすべて適合しています。
要素数（polyline 23 / text 103 / polygon 44 / path 24）とすべての座標は、
decorate (T6) の修正後に一致します。

**証拠。**
[`1367`](https://github.com/knowvah/dot-engine/blob/main/plans/fix-element-count-bucket/comparisons/1367.md)
の比較ページ（並置のレンダリングと証拠の記録）。

### A6. 縮退した入力での `unsigned int` によるキャンバスのオーバーフロー {#a6-unsigned-int-canvas-overflow-on-degenerate-input}

**影響を受けるもの：** `1314` — ファジングで得られた入力（`fontsize="991836031967s8"`）で、
その途方もないフォントサイズにより、描画が約 2.75e11 pt に膨れ上がります。

**何が起きるか。** C は `job->width` / `job->height` を **`unsigned int`** として保持します
(`gvcjob.h:327-328`)。巨大なポイントサイズの `ROUND(...)`（`emit.c:1249-1250`）は
32 ビットをオーバーフローして mod 2³² で折り返し、SVG バックエンドはそれを
**符号付き**の `%d` で出力します（`gvrender_core_svg.c:258-259`）— そのため C は
`height="-425618343"` と出力します。ポートは、数学的に整合した（折り返さない）値を保持します。
他のすべての値 — ノードの楕円の `cx/cy/rx/ry`、ルートの `translate`、多角形、
テキストの `font-size` — はバイト単位で同一で、最上位の `<svg>` の
width/height だけが異なります。

**追いかけない理由。** C の 32 ビット整数のオーバーフローを再現することは、移植する価値のある
レイアウトの挙動ではなく、入力も縮退しています。上流がオーバーフローを修正した場合
（たとえばフィールドを広げる、またはサイズをクランプする）には再検討します。

#### A6b. 縮退した NaN レイアウト（`sfdp`、病的な `repulsiveforce`） {#a6b-degenerate-nan-layout-sfdp-pathological-repulsiveforce}

**影響を受けるもの：** `2556` — `repulsiveforce=100`（⇒ 斥力が
`pow(dist, 101)` を使う）で、ばね-静電ソルバーが**両方のエンジンで NaN** に
陥ります。ネイティブのオラクル自身が、すべて `nan` のノード／エッジ位置と、
縮退したバウンディングボックスを出力します。

**何が起きるか。** すべての座標が NaN の場合、2 つの実装はそのゴミを
異なる形で直列化します。(1) グラフの bb／背景の多角形 — C は `NaN` を
`int` に丸め、arm64 では `INT_MIN` 規模のゴミになります（`bb="0,0,-4.295e+09,
-4.295e+09"`）。ポートは `0` を保持します。(2) エッジの描画オペレーション — ネイティブの
出力パスは、NaN のスプラインの `_draw_`/`_hdraw_` を抑制し（`pos` のみ出力）、
ポートは NaN の制御点のままそれらを出力します。ノードの描画は一致します（どちらも
抑制します）。どちらの側にも、実在するレイアウトはありません。

**追いかけない理由。** ポートはすでにネイティブと*同じ* NaN の発散を再現しています —
そこに至らせた修正は本物です（後述）。残っているのは、各々が NaN のゴミを
どう直列化するかだけです。C の `(int)NaN` の未定義動作と、その NaN スプラインの描画抑制を
再現することは、どちらのエンジンでもレイアウトが縮退している入力に対しては、意味のある
レイアウトの忠実さではありません。上流が `repulsiveforce` をクランプするか、
NaN の位置をサニタイズする場合には再検討します。

**これを到達可能にしたポートの修正（追いかけて済ませたものではない — 本物のバグ）。**
これらの修正前は、ポートは縮退状態に到達することすらできませんでした。(1) `armPow`
(`src/common/arm-pow.ts`) は、高速経路でないあらゆる引数で例外を投げていました。現在は、
ARM の `pow.c` の特殊ケースの分岐を完全に移植しており、`pow(NaN, y) = NaN` が libm と同じになります。
(2) `bezierClip` (`src/common/splines-geom.ts`) は、収束判定が C の `while (ABS > .5)` の
単純な否定だった（有限値では等価だが NaN では等価でない）ため、NaN の制御点で永久にループしていました。
現在は C を正確に反映し、NaN で終了します。どちらも C に忠実で、NaN の入力にのみ影響します。

### A7. `round()` のボックスの壁の丸め境界（`dot`） {#a7-round-box-wall-rounding-boundary-dot}

**影響を受けるもの：** `graphs-honda-tokoro` と、（2026-07-28 に追加、905 件の母集団に新規に加わった）
その `graphs/directed/` の兄弟 `tree-graphs-directed-honda-tokoro`
（どちらも structural-match、単一のエッジ `n012->n011` で maxΔ ≈ 1 pt）。
兄弟は `samearrowhead` 属性だけが異なり、これはこのペアのルーティングに影響しません —
その `n012->n011` のジオメトリは、ポート側もオラクル側も受け入れ済みの ID とバイト単位で同一であり、
したがって以下のメカニズムはそのまま当てはまります。

**何が異なるか。** `maximal_bbox` のヘッド側回廊のボックスの壁は、2 本の
`n012->n011` の平行エッジが共有する `samehead` ポートについて、C では内部の
x=90 に、ポートでは x=89 に着地します。共有ポートの構築 (`buildSharedPort`) と
平行エッジのグループ化はどちらも C にバイト単位で適合しており、1 px のギャップは純粋に
`round()` の丸め境界の副産物です — 上流の浮動小数点ノイズ約 1e-14 が、ちょうど `.5` の境界上に
ある値を隣の整数へ押しやります。ポートの `maximal_bbox` の式はすでに C のものを正確に
反映しています。

**追いかけない理由。** `round()` は、コーパス内のルーティングされるすべてのエッジが通る
プリミティブです。この 1 つのケースに合わせてその境界の挙動を動かすことは、
2 本のエッジの 1 px のために、コーパス全体にリグレッションの危険を負わせることになります —
`bbox-class-control-hull-vs-curve` に記載された制御ハルの丸めノイズと同じ共有プリミティブの
制約です。完全な診断：
`.agent-notes/honda-samehead-shared-port.md`。

### A8. `fp-contract`/FMA の丸め対厳密な IEEE（`dot`） {#a8-fp-contract-fma-rounding-vs-strict-ieee-dot}

**クラス。** clang arm64 は、オラクルのバイナリを `-ffp-contract=on` でコンパイルし、
選ばれた積和のシーケンスを単一の FMA 命令に融合します。ポートは V8 上で動作し、
V8 は厳密な IEEE-754 の丸めを行い、`fma` を出力できません。ビット単位で同一の入力でも、
コンパイラが融合を選んだ式のところで、両者は 1〜2 ULP 食い違います。ポート側は常に
厳密な IEEE-754 の結果で、オラクル側は常に FMA で融合された結果です。これは
C のソースコードのセマンティクスより下の層の、コンパイラ／ランタイムの移植性の制約であり、
ポートのロジックの欠陥ではありません — clang 固有の融合の選択をソフトウェアでエミュレートしない限り、
縮減できません。既知の事例は 2 つあり、2 つの異なる箇所で、2 つの異なる増幅メカニズムを
持っています。

- **2646** — ULP は `Proutespline` の `points2coeff`/`solve3` の三次方程式の解法の内部で生じ、
  スプラインフィッターの根の数を直接反転させます。
- **2620** — ULP は `poly_init` の多角形頂点の広がりのループ（ノードのサイズ決定）で生じ、
  下流で `ortho` の忠実な緩和ごとの整数の切り捨てによって増幅され、同コストの迷路回廊の
  同順位の反転になります。

**影響を受けるもの：** `2646`（structural-match、21,216 本のエッジのうち 3 本で maxΔ 42.09：
`edge2575` `g[4639]`、`edge3905` `g[7777]`、`edge15467` `g[30201]` — いずれも
レコードポートの `:c->:nb_part` の smode の長いエッジのルート）。**A3** の兄弟です。
どちらのクラスも `Proutespline` 内部の、縮減不能な浮動小数点の移植性による同順位ですが、
メカニズムは別です — libm の `hypot` ではなく、コンパイラの `fp-contract` の副産物です。

**何が異なるか。** 3 本のエッジすべてで、最後の `routesplines` の呼び出し
（ヘッドポートへの直線の区間）だけが乖離します。その終点はバリア多角形の下側の壁の上に
ビット単位で正確に乗っており、接線はその壁に平行です
（`evs[1]=(1,-1.22e-16)`）。そのため、すべての `splinefits` の候補は `t=1` でバリアに接しており
— 交差の三次方程式のほぼ二重根です。`points2coeff` はその三次方程式を壊滅的なキャンセレーションを通して
計算します（約 7446 の項が約 0.099 に潰れる）。オラクル（clang/arm64、
`-ffp-contract=on`）は `v3 + 3*v1 - (v0 + 3*v2)` を融合積和に融合しますが、V8 は
厳密な IEEE の丸めを行います — 両者は**ビット単位で同一の入力**で約 9.1e-13 食い違い、
そのノイズが `solve3` の判別式の符号を反転させます。C は根を 1 つ見つけます（866.7、セグメントの内側）。
ポートは 3 つの根を見つけ、`t=0.9999975 < 1-EPSILON2` に偽の相方の根があります。
その偽の根が `a` の半減の反復を 1 回余分に引き起こし、最後のピースの接線の大きさを
2 倍の係数で反転させ（3 本のエッジで向きはどちらにもなる）、クリップ後に maxΔ 42.09
（SVG の差分 26 件）を生みます。

**受け入れる理由（縮減不能であることは対照実験で証明済み）。** 6 回の `routesplines` の
呼び出しすべてを両側でダンプしました — ボックス、多角形、`PL`、開始、終了、`evs` は
バイト単位で同一で、それ以前の（最後ではない）呼び出しの出力スプラインも同じです。
乖離は最後の呼び出しの `solve3` の内部だけです。スタンドアロンの純粋な C ハーネスが
唯一の変数を切り分けました。`-ffp-contract=off` でコンパイルすると、3 本のエッジすべてで
**ポート**をビット単位で正確に再現し、デフォルトの (`on`) の融合は、3 本のエッジすべてで
**オラクル**をビット単位で正確に再現します。したがってポートはすでに厳密な IEEE-754 の C と
一致しており、乖離は完全に、オラクルのコンパイラの FMA の融合の選択によるものです。
C のソースコードのセマンティクスより下の層であり — 修正すべきソースレベルの不忠実さは
ありません。的を絞った修正（`points2coeff` で融合を手作業でエミュレートする）が試され、
反証されました。3 本のうち 2 本は直りますが、3 本目は直りません。3 本目の反転は
`solve3` 自身の内部の融合に由来します。完全な修正には、スプラインフィッター全体にわたる
ソフトウェアによる FMA のエミュレーションが必要で — サブピクセルで 3 本のエッジという見返りのために、
ホットループのコストと、コーパス全体に及ぶ丸めの影響範囲を負うことになります。
完全な診断：`plans/residual-cleanup/analysis/2646-fp-contract.md`。

**影響を受けるもの（歴史的）：** `2620`（かつては structural-match、maxΔ 585。24 本のエッジパスと
22 個の矢じりで差分 423 件）。**2026-07-11 に conformant に収束しました。**
忠実な `sgraph` の隣接バッファのスピルと `chancmpid` の双方向包含の移植
（`.agent-notes/ortho-maze-circo-rca.md` を参照）が差異を取り除きました。
受け入れエントリーは退役し、この節は A8 クラスの文書として残されています。

**何が異なるか。** `ortho` (`splines=ortho`) のパイプラインは、同一の入力が与えられれば
C にバイト単位で適合します — C の正確な迷路の入力（座標、`xsize`/`ysize`）を
ポートの ortho 段に注入することで証明されました。378/378 本のルート済みセグメントが
バイト単位で同一に出てくるため、`src/ortho` には何の欠陥もありません。
実際の乖離は、迷路の*入力*における 1〜2 ULP です。C の `poly_init` の多角形頂点の広がりのループ
(`shapes.c`) で計算されるノードの `ysize`（およびランク内での累積によって `ND_coord.y`）で、
`-ffp-contract=on` の下では `R.x += sidelength*cosx` が FMA に融合され、ポートの厳密な
IEEE 演算より約 1 ULP 大きくなります（両側とも算術的に同一の式を実装しています）。
`2620` には小数幅の多角形ノードが 173 個あり、すべてで C ≥ ポートが 1〜2 ULP の差です。
その ULP は、`ortho` のダイクストラの緩和によって増幅されます — 導入されるのではなく —。
緩和はステップごとに実行中の距離を忠実に切り捨て（`sgraph.c:165`、ポートでは
`Math.trunc` として反映）、重みは生のセルの広がりから導かれます
（`maze.c:257`）。ULP だけずれたジオメトリが、4 本のルート済みエッジ（パスとその矢じり）で
同コストの回廊の同順位を反転させ、残る差分は、その 4 つの反転から波及する
±1 トラックの番号の振り直しです。

**受け入れる理由（縮減不能であることは対照実験で証明済み）。** `-ffp-contract` のみを変えた
スタンドアロンの C ハーネスが、乖離した六角形の頂点で両側を再現しました。
`-ffp-contract=on` → `310.29250168188713`（オラクルと一致）、
`-ffp-contract=off` → `310.29250168188707`（ポートと一致）で、乖離する演算は頂点 `i=3`
（`R.x=-0.50000000000000011` 融合 対 `-0.5` 非融合）に切り分けられました。2 つ目の
入力注入実験（唯一の変数：ortho の入力値）が増幅器を確認しました。ポート自身の
`orthoEdges` に C の正確な `coord`/`xsize`/`ysize` を与えると、4 つの回廊の乖離はすべて 0 になります —
ortho のコードに欠陥はなく、単に（C 自身の迷路コストのルーティングと同様に）
入力の 1〜2 ULP のずれに敏感なだけです。一致させるには、`poly_init` 内の 1 つのコンパイル済みの
式ツリーに対する clang 固有の FMA の融合をエミュレートすることになります —
ソースのセマンティクスを移植するのではなく、コンパイルの副産物を追いかけることです。
完全な診断：`plans/ortho-2620-residual/analysis/2620-ortho-route.md`。

**エミュレートした例外（受け入れていない）：`triang.c:ccw`。** 1 つの融合箇所は、
受け入れるのではなくビット単位で再現されています。pathplan の `ccw` は
`fnmul`+`fmadd`（正確な第 1 の積 − 丸められた第 2 の積）にコンパイルされるため、
線分の端点とビット単位で等しいクエリ点は、ISON ではなく ISCW/ISCCW と判定されます。
その結果、`shortest.c:pointintri` は多角形の頂点の端点を拒否し
（"destination point not in any triangle"）、`makeMultiSpline` は結合されたすべての 2 サイクルで
通常のルーティングにフォールバックします — ポートが一致させなければならない、
大きく、離散的で、コーパス全体に及ぶ挙動です。上記の `solve3`/`poly_init` の箇所
（コンパイル済みの式ツリーの奥深くにあり、修正は反証された）と異なり、`ccw` は
明快なセマンティクスを持つ単独のコンパイル済み関数であるため、`src/pathplan/triang.ts` が
それをエミュレートします。通常の double の高速経路に、通常の符号と融合の符号が証明可能に
一致する箇所での保守的な誤差境界を組み合わせ、ゼロ近傍のケースには
正確な Dekker の積 + 2 進 BigInt の経路を用います。

### A9. libm の三角関数の 1 ULP → CDT の同一円周上の同順位の反転（`circo`/`twopi` のマルチスプライン） {#a9-libm-trig-1-ulp-→-cdt-cocircular-tie-flip-circo-twopi-multispline}

**クラス。** V8 の `Math.sin`/`Math.cos` は、Apple libm の `sin`/`cos` とビット単位で同一では
ありません（証明済み：8 つの楕円障害物の角の角度の 1 つ、`2π·4.5/8` での 1 ULP の不一致）。
`makeObstacle` の外接 8 角形の角はその ULP を引き継ぐため、三角形ルーターの入力座標は
オラクルと最大 6e-14 異なります。対称なレイアウト（ランク／リング上の同じ大きさのノード）では、
ルーターの四角形が実数演算では**ちょうど同一円周上**になるため、厳密な内接円の述語は

オラクルでは `Pshortestpath` に失敗する回廊の多角形（"destination point not in any triangle" →
通常のスプラインへのフォールバック）が、ポートでは成功します（またはその逆）。
結果として得られるスプラインは約 0.2〜0.5pt 異なります。**A3**/**A8** の兄弟です。
C のソースのセマンティクスより下の、縮減不能な浮動小数点の移植性の制約であり —
一致させるには、Apple libm の `sin`/`cos` の正確な丸めを JS で再現する必要があります。

**影響を受けるもの：** `241_0`（circo Δ≈0.2 / twopi のキャンバス Δ≈9。エッジ
`5:ne->8:nw` の回廊の反転による）、`2343`、`2239`、`share-b29`、`windows-b29`（twopi、

## 追跡中のロングテール（`dot` の属性とエッジケース） {#tracked-long-tail-dot-attribute-edge-case}

**デフォルト**では、`dot` エンジンはゴールデンコーパス上で、厳密な決定的許容誤差の範囲で
C のバイナリと一致します（`conformant` 判定。冒頭の注記を参照）。残る差異は、
**属性とエッジケースのロングテール**であり — あらゆる Graphviz のポートで歴史的に
難しい部分です。上の受け入れ済みの差分と異なり、これらは*解消されます*。
件数とともに、
[`PARITY-dot.md`](https://github.com/knowvah/dot-engine/blob/main/test/corpus/PARITY-dot.md)
でライブに追跡されています。

| カテゴリ | 何が異なるか |
|---|---|
| **path-structure** | 特定の構成でのエッジのスプラインルーティング（たとえば、一部のフラットエッジや密な回廊のケース）。 |
| **element-count** | 特定のグラフで、C より多い／少ない SVG 要素を出力する機能。 |
| **color-stroke** | 特定のスタイル属性に対するストローク／塗りの出力の違い。 |
| **parser-gap** | パーサーがまだ完全には受け付けない DOT 入力が少数。 |

グラフが一般的な属性と `dot` エンジンだけを使っているなら、ほぼ確実に決定的許容誤差による一致の経路にあります。
レイアウトがおかしく見える場合は、その入力クラスについて `PARITY-dot.md` を確認してください —
未知のものではなく、オラクルで固定された修正ミッションを伴う追跡中の項目である可能性が高いです。

> **ラベル主導のケースについての注記。** テキスト計測のクラス (A2) はクローズ済みです —
> それに基づいて受け入れられている `dot` のグラフはもうありません。現在
> structural-match にあるグラフは、フォントメトリクスの差分ではなく、追跡中のギャップです。

### `concentrate=true` での対向エッジの矢じり {#concentrate-true-opposing-edge-arrowheads}

`concentrate=true` が逆平行のペア (`A->B; B->A`) を 1 本の生き残るエッジにマージするとき、
そのエッジは**両端**に矢じりを描かなければなりません。これは現在移植済みです
（`arrow_flags` の `conc_opp_flag` の分岐。`src/common/splines-clip.ts:arrowFlags` を参照）。
そのため `graphs-b135`、`167`、`2087` は一致します（矢じりが欠落する `element-count` の差異と、
クリップされていないスプラインの `@d` の副作用は、どちらも解消しました）。

一部の concentrate グラフは、矢じりの修正では対処されない**別の、既存の残差を保持しています** —
それは矢じりの欠陥ではなく、ノードの **x 座標**の位置の差分（x 方向ネットワーク単体法 /
コンパスポート）です。

- **`graphs-b15`、`graphs-b69`** — 大きなレコード／クラスターの「エレベーター」グラフ。
  concentrate は作動し、正しくマージします。残差は約 1pt のノード x の差分で、
  それが `element-count`/スプラインの `@d` の差異へと増幅されます。矢じりの出力そのものは
  現在は正しいです（b69 は欠けていた矢じりの多角形を得ます）。x 座標の根本原因については
  `b69-concentrate-undermerge` のエージェントノートを参照してください。
- **`1453`** — 依然として、conc_opp_flag の矢じりとは無関係の、最上位の
  `element-count` が原因で乖離します。
- **`2825`** — この矢じりの修正の時点では、conc_opp_flag とは無関係の最上位の
  `element-count` が原因で乖離していました（そこでは対向ペアのマージは
  起きません）。その後 fix-2825-rebuild-vlists ミッションによりクローズされました。
  上の A4 を参照してください。

これらは x 座標／構造に関する追跡中の項目であり、矢じりのバグ**ではありません**。

### 2.0 フィデリティミッションからのレイアウト忠実度のギャップ（neato、sfdp、fdp、twopi、circo） {#layout-fidelity-gaps-from-the-2-0-fidelity-mission-neato-sfdp-fdp-twopi-circo}

2.0 フィデリティミッションは、未移植の属性値を明示的に失敗させるようにしました
（[エラーと例外](https://github.com/knowvah/dot-engine/blob/main/docs-site/guide/errors.md)の
`UNSUPPORTED_FEATURE` の表を参照）。次の項目が残され、
`plans/v2-fidelity/decision-journal.md` に記録されています。

**明示的に失敗するもの（未移植）。** オーバーラップするノードを伴う `overlap=voronoi` は、
neato、twopi、circo、sfdp で依然として `UNSUPPORTED_FEATURE` を投げます。Voronoi の調整器
自体（`vAdjust` のアルゴリズム）が移植されていません。例外を投げるかどうかを決める
オーバーラップの判定は、C 自身のもの（`poly.c` のノード多角形に対する `countOverlap`）です。

**既知のギャップ（依然として暗黙のもの）。** ポートはこれらをエラーなしでレンダリングし、
ネイティブの Graphviz とは異なります。`v2-silent-gaps` ミッション
（`plans/v2-silent-gaps/decision-journal.md`）で発見されたもので、受け入れ済みの差分ではありません。

- **`getAdjustMode` の "Unrecognized overlap value" の警告は出力されません。**
- **回転した多角形の頂点は、ネイティブと最下位ビットが異なることがあります
  （縮減不能：ホストの数学ライブラリ）。** `poly_init` は各頂点を
  `atan2`、`hypot`、`sin`、`cos` で配向します。ビット単位で同一の入力でも、macOS の libm と
  V8 は異なる最下位ビットを返し（例：`atan2(0x3fd6a09e667f3bce,
  0xbfd6a09e667f3bca)`：libm `…21d1`、V8 `…21d2`。次の頂点での `hypot`：
  libm `…fffd`、V8 `…fffe`）、そのため `orientation=20` のボックスは、頂点の y が
  ポートでは `-18`、ネイティブでは `-17.999999999999996` になります。ネイティブの Graphviz 自身も
  プラットフォームの libm によって変わり、ブラウザーはそれを呼び出せません。ポート自身の
  演算は C と一致します（`RADIANS` の順序は固定。サンプルした 1664 個の頂点座標のうち 776 個が
  ビット単位で同一で、残りは libm のみを介して異なる）。影響：ちょうど接する `polyOverlap` の
  判定が反転しうる。ネイティブの頂点を使えばすべての判定が一致します。
- **sfdp は macOS 上でネイティブと異なることがあります（縮減不能：ホストの libm の `pow`）。**
  計装したネイティブの sfdp で診断しました。位置は、斥力の 1 つの項
  `pow(dist, 1 - p)`（`spring_electrical.c`、`p = -1` なので `pow(x, 2)`）が、macOS の libm から
  `x*x` より 1 ulp 小さい値を返すまで、ビット単位で同一のままです
  （`pow(1.4116727416983157, 2)`：libm `1.9928199296540394`、正しく丸めた値は
  `…396`。macOS の `pow(v, 2) != v*v` は、サンプルした 16201 個の `v` のうち 20 個）。
  これが反復の `Fnorm` を最下位ビットで変え、sfdp の適応的な冷却がそれを
  異なる（しばしば鏡像の）レイアウトへと増幅します。ポートの `armPow` は ARM の
  optimized-routines の `pow`（glibc ≥ 2.28）、つまり Linux の Graphviz が計算するものであり、
  macOS のオラクルのほうが外れ値です。除外したもの：シード（明示的な `start=` の値は
  一致する）、`pcp_rotate`（同じ入力は同じ出力を与える）、位置と引力の項
  （ビット単位で同一）。例：デフォルトのシードでの単独の三角形 `a--b; a--c; b--c`。
- **fdp は、ホストの libm の `cos`/`sin` を介してネイティブと異なることがあります。** fdp は
  15.0.0 以降の Graphviz（hypot 距離の斥力、`Mlimit`）に従っており、ホストの
  libm の `hypot` がビット単位で再現されています（`src/common/libm-hypot.ts`、40 万サンプルで
  不一致 0）。fdp でレンダリング可能な 252 個のゴールデン入力のうち 251 個は
  ネイティブのビルドと正確に一致します。残る 1 つ
  (`parallel-cluster-ldbxtried`) は、クラスターのポートノードを
  `T_Wd * cos(alpha)` で配置し、macOS の libm の `cos(-2.3840764867756761)` は
  V8 の `Math.cos` と 1 ulp 異なります。fdp の力のループがそれを約 3 インチに増幅します。
  Apple の `cos` は、`hypot` のように短いモデルから再現することはできません。
- **ポートが定義するネイティブのクラッシュ。** ネイティブの Graphviz は、
  `mode=KK` で `model=mds` かつエッジの `len` がある neato（`mds_model` が `GD_dist` を
  1 始まりの連番でインデックスする：ヒープオーバーフロー）、および切断されたグラフでの
  `model=circuit` で、終了コード 139 で終了します。ポートは前者では範囲外のセルを捨て、
  後者では最短経路にフォールバックします。比較すべきネイティブの出力はありません。

## 意図的に移植しないもの（非目標） {#intentionally-not-ported-non-goals}

これらはバグではなく、意図的なスコープの境界です。このライブラリが対象とするのは **SVG**
（および `json` / `xdot` / `dot` / imagemap の中間テキスト形式）です。

- **その他の出力形式。** ラスター（PNG/JPG/GIF/WebP/BMP）、PostScript/PDF/EPS、
  および GUI／対話型のバックエンドは対象外です。ラスターが必要なら、SVG の出力を使い、
  下流で変換してください。
- **SVG での `page=` によるページ分割。** ネイティブの `dot` も SVG をページ分割しない
  （SVG デバイスはページ分割のフラグを設定しない）ため、`page=` はこの経路では
  どちらの実装でも何もしません — よくある混乱の元であるためにここに記載しているだけです。
- **`-Tplain` のテキスト出力。** 延期されたもの（忠実なテキスト形式）であり、除外されたものではありません。
- **`gvpr`**（グラフ処理のスクリプト言語）— 対象外です。
- **C++ の便利なラッパー**（`cgraph++`、`gvc++`）— まず C の API が移植されます。
  必要なら、慣用的な TypeScript の便利なレイヤーは別のパッケージになります。
- **ブラウザーのテキスト計測での `fontnames=svg|ps`。** ブラウザーでは、
  canvas の計測器は、PostScript のエイリアスの `fontnames=native` のファミリーリスト
  （`Times-Roman` → `Times, serif`）からフォントを構築します。これは SVG のエミッターが
  デフォルトでレンダリングするのと同じ書体です。`TextMeasurer` はグラフのコンテキストを持たないため、
  `fontnames=svg` や `fontnames=ps` を設定したグラフは、SVG が svg/ps のファミリー名を出力する一方で、
  ネイティブのリストに対して計測されます。CSS が定義しないエイリアスのウェイト
  （`book`、`demi`、`light`、`medium`、`roman`）は、C と同様にそのまま出力されます。
  ブラウザーはそれらを無視して通常のウェイトでレンダリングし、計測器もそれに合わせて
  通常のウェイトで計測します。Node の出力は影響を受けません（canvas の計測器は決して使いません）。
- **ネイティブ専用のメカニズム**は、ブラウザーで安全な同等のものに置き換えられています。
  動的なプラグインのロード (`dlopen`) は静的なエンジン／レンダラーの登録に、
  ファイルシステムの読み取り（フォント、画像、設定）は呼び出し側が提供するコールバック
  （たとえば `setImageSizer`）に置き換えられます。挙動は保たれ、メカニズムが異なります。

## 差異の報告 {#reporting-a-divergence}

C と異なる出力を見つけ、それが上記の受け入れ済みの差分でも、`PARITY-dot.md` にあるものでも、
非目標でもない場合、それは報告する価値のあるバグです — C のソースが仕様であり、
一覧にない差異は、受け入れられた挙動ではなく欠陥として扱われます。
