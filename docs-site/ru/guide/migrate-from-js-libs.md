# Миграция с других JS-библиотек для Graphviz

viz.js / `@viz-js/viz`, `@hpcc-js/wasm` (`@hpcc-js/wasm-graphviz`) и
`d3-graphviz` дают JavaScript доступ к Graphviz, компилируя настоящий C-код
Graphviz в **WebAssembly** и вызывая его. @knowvah/dot-engine — это написанный с
нуля **порт на TypeScript**: механизмы компоновки, парсер и генератор SVG
представляют собой исходный код на TypeScript, а не скомпилированный бинарник.

Эта разница — главное, а не сноска:

| | WASM-обёртки (viz.js / `@hpcc-js/wasm` / d3-graphviz) | @knowvah/dot-engine |
|---|---|---|
| Реализация | Настоящий C-Graphviz, скомпилированный в бинарник `.wasm` | Чистый порт на TypeScript, без скомпилированных артефактов |
| Инициализация модуля | Асинхронная — перед первым использованием нужно создать экземпляр WASM-модуля и дождаться его | Нет — `import` и синхронный вызов |
| Бандл | Нужно поставлять ресурс `.wasm` (от сотен КБ до нескольких МБ) вместе с JS | Только JS, с поддержкой tree-shaking |
| Отладка | Пошаговое выполнение WASM-блоба (или исходного кода на C, если он у вас есть) | Пошаговое выполнение настоящего TypeScript с source map |
| Модель потоков | Некоторые сборки выполняют компоновку в Web Worker | Выполняется в вызывающем потоке, как любая функция TS |
| Форматы вывода | Любые, с которыми был скомпилирован C-код, — обычно полный набор Graphviz, включая растр и PDF | SVG + текстовые форматы DOT/json/xdot/plain/imagemap — см. ниже |

Если ваш сценарий — «вызвать функцию, получить SVG, без асинхронных церемоний и
без WASM-ресурса, который нужно размещать», то именно для этого создан
@knowvah/dot-engine. Если ваш сценарий зависит от растрового вывода или PDF, см.
ниже раздел [Когда стоит остаться на WASM](#when-to-stay-on-wasm).

## Различия в API

У этих трёх библиотек разный вид; в таблице ниже — типичный случай миграции
(приблизительно — сверяйтесь с документацией каждой библиотеки; ссылки на
источники см. под таблицей).

| Библиотека | Типичный вызов | Эквивалент в @knowvah/dot-engine |
|---|---|---|
| `@viz-js/viz` (преемник viz.js) | `Viz.instance().then(viz => viz.renderSVGElement(dot))` — асинхронно, `Viz.instance()` возвращает Promise | `renderSvg(dot, 'dot')` — синхронно, без шага создания экземпляра или инициализации |
| viz.js 2.x (устаревшая, `new Viz()`) | `new Viz().renderString(dot)` — возвращает `Promise<string>` | `renderSvg(dot, 'dot')` — синхронно |
| `@hpcc-js/wasm-graphviz` | один раз `await Graphviz.load()`, затем `graphviz.dot(dot)` (после загрузки синхронно) | `renderSvg(dot, engine)` — вообще без шага загрузки или прогрева |
| `d3-graphviz` | `d3.select(sel).graphviz().renderDot(dot)` — привязывает результат к DOM, анимирует переходы | `renderSvg(dot, engine)` возвращает **строку** SVG; вставлять её в DOM вы будете сами (например, `el.innerHTML = svg`) |

Каждый вызов @knowvah/dot-engine в правом столбце **синхронный** — ждать нечего,
потому что нет WASM-бинарника, который нужно создавать. Уберите любые
`await`/`.then()` вокруг вызова @knowvah/dot-engine: они никогда не были нужны.

- `Viz.instance()` → Promise и метод `renderSVGElement()` в `@viz-js/viz`
  описаны на viz-js.com; подтверждено опубликованным в проекте примером
  использования на момент написания.
- `new Viz().renderString(dot)` из viz.js 2.x — это API, описанное для той
  (теперь вытесненной) линейки релизов; если у вас актуальная установка,
  проверьте, не используете ли вы на самом деле `@viz-js/viz`.
- Пара `Graphviz.load()` / `graphviz.dot()` из `@hpcc-js/wasm-graphviz`
  подтверждена опубликованным в пакете примером использования на момент
  написания. Отдельный, более старый пакет `@hpcc-js/wasm` в прошлых релизах
  дополнительно предоставлял вызов `graphviz.layout(dot, format, engine)` —
  прежде чем полагаться на точную сигнатуру, проверьте документацию установленной
  у вас версии.
- Цепочка `.graphviz().renderDot(dot)` из `d3-graphviz` и то, что внутри она
  построена на `@hpcc-js/wasm`, подтверждены опубликованным README проекта на
  момент написания.

### Привязка `renderDot` к DOM здесь вне области рассмотрения

`d3-graphviz` делает больше, чем рендерит SVG: он привязывает результат к
выборке D3, сравнивает повторные рендеры и анимирует переходы между
компоновками. У @knowvah/dot-engine нет никаких предпочтений относительно DOM —
`renderSvg`/`render` возвращают обычную строку. Если вам нужны анимированные
переходы между двумя компоновками в стиле d3-graphviz, эту логику придётся
строить поверх двух вызовов `renderSvg` и собственного сравнения DOM (или
продолжать использовать d3-graphviz именно для этой возможности — см. ниже).

## Получение данных компоновки без разбора строкового формата

Все три WASM-библиотеки умеют выдавать собственные форматы Graphviz — JSON или
простой текст, — после чего вы сами разбираете эту строку, чтобы получить
координаты узлов и рёбер. @knowvah/dot-engine обходится без текстового обходного
пути: вызовите `getLayout(g)` (после `render`), и вы сразу получите
типизированный, сериализуемый в JSON снимок — без строки `-Tjson`/`-Tplain`,
которую нужно разбирать.

```ts
import { createGraph, render, getLayout } from '@knowvah/dot-engine';

const b = createGraph({ directed: true });
b.addNode('a');
b.addNode('b');
b.addEdge('a', 'b');

render(b.graph, 'svg');
const layout = getLayout(b.graph);
// layout.nodes  → [{ name: 'a', x, y, width, height }, ...]
// layout.edges  → [{ tail: 'a', head: 'b', points: [...] }]
// layout.bounds → { x, y, width, height }
```

Полную форму снимка, единицы измерения и параметр `yAxis` см. в разделе
[Чтение вычисленной геометрии](/ru/guide/geometry).

## Когда стоит остаться на WASM {#when-to-stay-on-wasm}

Будьте честны с собой насчёт области применения: @knowvah/dot-engine
ориентирован на SVG и текстовые форматы `dot`/`xdot`/`json`/`plain`/`plain-ext`/`imap`/`cmapx`.
Он **не** выдаёт растровые форматы (PNG/JPEG/GIF/...) или PostScript/PDF/EPS —
это намеренная граница области применения, а не просто недоработка. Точный
список того, что не входит в цели проекта, см. в разделе
[Известные расхождения](/ru/divergences).

Если вашему приложению нужен вывод `-Tpng` или `-Tpdf` непосредственно из
механизма компоновки, WASM-библиотеки, перечисленные выше, по-прежнему
закрывают этот случай: поскольку они запускают настоящий C-Graphviz, они
поддерживают любые форматы вывода, с которыми была скомпилирована эта сборка. В
таком случае либо продолжайте использовать WASM-библиотеку для этой одной ветки
кода, либо рендерьте в `'svg'` с помощью @knowvah/dot-engine и конвертируйте
SVG в растр или PDF дальше по цепочке отдельным инструментом.
