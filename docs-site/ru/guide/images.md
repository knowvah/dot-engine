# Изображения

Узел с `image="logo.png"` (или ячейка `<IMG SRC="logo.png">` в HTML-подобной метке) по
умолчанию не получает встроенных пикселей. @knowvah/dot-engine выдаёт источник
**дословно**:

```html
<image xlink:href="logo.png" width="64px" height="64px" .../>
```

То, что отображает SVG, — браузерный `<img>`/встроенный `<svg>`, оболочка Electron,
сборка статического сайта — само разрешает этот `href`. На этой странице описано, как
этот href получает размер во время компоновки, три способа сделать так, чтобы пиксели
действительно появились, и последствия каждого из них для CSP.

## Как проходят изображения

1. Граф объявляет `image="logo.png"` у узла, либо HTML-подобная метка содержит ячейку
   `<IMG>`.
2. Для ячейки `<IMG>` в HTML-подобной метке Graphviz нужны **собственные ширина и
   высота** изображения, чтобы задать размер ячейки, прежде чем компоновать что-либо
   ещё — библиотека никогда не обращается ни к файловой системе, ни к сети, чтобы это
   узнать, поэтому вы регистрируете sizer (`setImageSizer`, о нём рассказано в разделе
   [Использование в браузере](/ru/guide/browser) и ещё раз ниже — для Node). Атрибут
   узла `image=` sizer'ом **не** измеряется: как в нативном Graphviz без графической
   среды, узел сохраняет обычную рамку, а изображение рисуется внутри неё.
3. Компоновка выполняется с размерами, которые вернул ваш sizer для каждого `<IMG>`.
4. Генератор SVG (`usershape()` из `src/render/svg.ts`) записывает
   `<image xlink:href="...">` с рамкой, вычисленной на шаге 3. По умолчанию `href` —
   это исходная строка `src`, экранированная для XML, и больше ничего.
5. Необязательно — если вы вызвали `setImageResolver` и выполнили рендеринг с
   `{ inlineImages: true }` — генератор вместо этого записывает
   `xlink:href="data:<mime>;base64,<bytes>"` — самодостаточный URI `data:`. Это
   дополнительная возможность; нативный Graphviz так не делает.

Определение размеров и встраивание — две независимые, регистрируемые по отдельности
точки расширения: можно определять размеры изображений без встраивания (обычный
случай — файл размещается на хосте) или делать и то и другое (самодостаточный SVG).

## Определение размеров в Node и в браузере

`setImageSizer` принимает `(src: string) => { w: number; h: number } | null` и
вызывается один раз для каждого различного источника `image=`/`<IMG>` во время
компоновки. Это регистрация на уровне всего процесса — тот же шаблон, что у
`setImageResolver` ниже, — вызовите её один раз перед `render()`/`renderSvg()`.

**Браузер** — измерьте настоящее изображение, раз у вас уже есть `Image` и
`decode()`:

```ts
import { setImageSizer } from '@knowvah/dot-engine';

const cache = new Map<string, { w: number; h: number }>();

async function warmImageSizes(sources: string[]): Promise<void> {
  for (const src of sources) {
    const img = new Image();
    img.src = src;
    await img.decode();
    cache.set(src, { w: img.naturalWidth, h: img.naturalHeight });
  }
}

// setImageSizer itself must be synchronous, so pre-warm the cache first
// (e.g. await warmImageSizes([...]) before calling render/renderSvg).
setImageSizer((src) => cache.get(src) ?? null);
```

`setImageSizer` — синхронный обратный вызов, внутри него нет `await`, поэтому в
браузере размеры заранее определяются (через `decode()`) в кэш до начала компоновки,
а затем синхронно читаются из этого кэша.

**Node** — здесь нет DOM-объекта `Image`, а библиотека не будет читать файловую
систему за вас. Либо жёстко задайте известные размеры, либо прочитайте их сами
(например, из манифеста или из лёгкого разборщика заголовков PNG/JPEG, который вы
предоставляете) и передайте результат тем же способом:

```ts
import { setImageSizer } from '@knowvah/dot-engine';
import { readFileSync } from 'node:fs';

// Simplest: fixed dimensions known ahead of time.
setImageSizer((src) => (src === 'logo.png' ? { w: 64, h: 64 } : null));

// Or: derive dimensions in your app layer (disk, S3 head request, a
// manifest file you maintain) and hand back the result synchronously.
const manifest = new Map(
  Object.entries(JSON.parse(readFileSync('image-manifest.json', 'utf8'))),
);
setImageSizer((src) => (manifest.get(src) as { w: number; h: number }) ?? null);
```

Если ваши графы никогда не ссылаются на внешние изображения, пропустите это целиком.

## Асинхронные sizer и resolver (на каждый рендеринг)

`setImageSizer` / `setImageResolver` — синхронные регистрации на уровне всего процесса,
поэтому в браузерном шаблоне выше приходится заранее заполнять кэш. Асинхронные точки
входа принимают хуки **при каждом вызове** и ждут их за вас:

```ts
import { renderSvgAsync } from '@knowvah/dot-engine';

const { svg } = await renderSvgAsync(
  'digraph { a [label=<<TABLE><TR><TD><IMG SRC="logo.png"/></TD></TR></TABLE>>] }',
  'dot',
  {
    imageSizer: async (src) => {
      const img = new Image();
      img.src = src;
      await img.decode();
      return { w: img.naturalWidth, h: img.naturalHeight };
    },
    inlineImages: true,
    imageResolver: async (src) => {
      const res = await fetch(src);
      return { bytes: new Uint8Array(await res.arrayBuffer()), mime: res.headers.get('content-type') ?? undefined };
    },
  },
);
```

- Каждый хук вызывается **не более одного раза для каждого различного `src`**,
  параллельно, до начала компоновки. Затем механизм выполняет обычную синхронную
  компоновку на основе собранных результатов.
- Хук, который **выбрасывает исключение или отклоняет промис**, считается промахом
  (`null`), в точности как синхронный хук, возвращающий `null`: нулевой размер для
  sizer'а, передача исходного `src` как есть — для resolver'а.
- Если задан асинхронный хук, промах **не** переходит к глобальным `setImageSizer` /
  `setImageResolver`. Если он не задан, действуют глобальные, как в `renderSvg`.
- Хуки действуют только для этого одного рендеринга; ничего глобального не
  регистрируется.
- `imageResolver` вызывается, только когда `inlineImages` равно `true`.
- `renderSvgInto` принимает те же параметры.

## Как сделать так, чтобы изображение появилось

Определение размеров обеспечивает правильную компоновку; оно не делает так, чтобы
пиксели появились там, где в итоге отображается SVG. Выберите один из трёх подходов.

### 1. Разместить файл на хосте

Отдавайте изображение по URL (или по пути, относительному к месту, где отображается
SVG), который браузер/потребитель может запросить. Это самый простой вариант, он не
требует дополнительной работы во время рендеринга — но контекст отображения должен
иметь доступ к этому источнику, а если SVG показывается там, где действует строгий
CSP `img-src`, этот источник должен быть добавлен в список разрешённых и там (см.
ниже).

### 2. Встроить как URI `data:`

Используйте API встраивания, чтобы получить одну самодостаточную строку SVG без
какой-либо внешней загрузки: `setImageResolver` предоставляет исходные байты, а
`render(g, 'svg', { inlineImages: true })` встраивает их.

```ts
import { render, setImageResolver } from '@knowvah/dot-engine';
import type { ImageResolver } from '@knowvah/dot-engine';

const images = new Map<string, Uint8Array>([
  ['logo.png', /* Uint8Array of the PNG bytes, e.g. fetched or bundled */ new Uint8Array()],
]);

const resolver: ImageResolver = (src) => images.get(src) ?? null;

setImageResolver(resolver);

const svg = render(g, 'svg', { inlineImages: true });
```

`ImageResolver` может также вернуть `{ bytes: Uint8Array; mime?: string }`, если вы
хотите явно указать MIME-тип (иначе генератор выводит его из расширения файла
источника — `.png` → `image/png`, `.svg` → `image/svg+xml` и так далее, а для
неизвестных расширений использует `application/octet-stream`). Чтобы сбросить
регистрацию, вызовите `setImageResolver(null)`.

::: tip
Предпочитайте встраивание, когда SVG попадает туда, где нельзя загружать внешние
ресурсы во время отображения, — почтовые клиенты, офлайн-документация, встраивание со
строгим CSP или любое место, где нужна одна самодостаточная строка без последующих
сетевых запросов. Цена — размер вывода: base64 раздувает изображение примерно на 33 %,
и оно дублируется в каждый SVG, который на него ссылается (без повторного использования
кэша браузера между рендерингами).
:::

`inlineImages` по умолчанию равно `false`; если не задано, вывод побайтово совпадает с
прежней передачей без встраивания. Параметр влияет только на формат `svg` — на
`json`/`xdot`/`dot`/другие текстовые форматы он не действует. Промах (resolver не
зарегистрирован или resolver возвращает `null` для данного `src`) автоматически
приводит к передаче исходного `src` как есть — встраивание деградирует плавно и никогда
не выбрасывает исключение.

### 3. Базовые каталоги в стиле `imagepath`

Атрибут графа `imagepath` нативного Graphviz сообщает бинарнику на C каталог поиска в
стиле файловой системы/`GDFONTPATH`, относительно которого разрешаются относительные
значения `image=`. @knowvah/dot-engine не реализует `imagepath` — порт сам никогда не
читает данные изображений с диска, поэтому нет пути, относительно которого можно было
бы разрешать (полные границы применимости см. в разделе
[Известные расхождения](/ru/divergences)). Если ваши графы используют относительные
пути `image=`, разрешайте их относительно собственного базового каталога/URL в том слое,
который формирует исходный код DOT, или в ваших обратных вызовах
`setImageSizer`/`ImageResolver` — оба получают исходную строку `src` в точности так, как
она записана в графе, поэтому дописать к ней базовый путь перед поиском — обычный,
допустимый приём.

## Рекомендации по CSP

Если ваши графы задаются пользователем (песочница, встраивание, которое отрисовывает
произвольный DOT), заранее продумайте политику `img-src` страницы.

**Встроенные изображения (URI `data:`)** требуют только:

```
img-src 'self' data:
```

В виде заголовка HTTP-ответа:

```
Content-Security-Policy: img-src 'self' data:
```

Или в виде метатега на странице, содержащей SVG:

```html
<meta http-equiv="Content-Security-Policy" content="img-src 'self' data:">
```

Это жёсткая политика — ни один внешний хост изображений не запрашивается, потому что
байты уже встроены в строку SVG.

**Изображения на хосте (вариант 1 выше)**, напротив, требуют, чтобы контекст
отображения мог загружать их оттуда, где они реально лежат. Если граф, заданный
пользователем, может ссылаться на произвольный URL в `image=`, перечислять каждый
возможный хост зачастую непрактично, поэтому странице песочницы/встраивания может
понадобиться что-то более мягкое:

```
Content-Security-Policy: img-src 'self' data: https:
```

::: warning
Никогда не делайте `img-src *` (или любой столь же мягкий `img-src`) значением по
умолчанию для **всего сайта**. Ограничьте его конкретной страницей песочницы/встраивания,
которой нужно отрисовывать произвольные графы, заданные пользователем, воспринимайте это
как намеренное, задокументированное ослабление только для этой страницы и держите CSP
всех остальных страниц строгим. Мягкий `img-src` позволяет вредоносному графу выводить
данные через побочные каналы URL изображений (например, кодируя данные в параметрах
запроса к хосту под контролем злоумышленника) или загружать нежелательное удалённое
содержимое. Если вы контролируете набор изображений, предпочитайте встраивание (`data:`)
и держите `img-src 'self' data:` везде.
:::

## Отсутствующие изображения

Если `setImageSizer` возвращает `null` (или sizer не зарегистрирован) для
указанного источника, @knowvah/dot-engine идёт тем же, соответствующим C, путём, что и
промах `gvusershape` в нативном Graphviz: выводит предупреждение и считает изображение
**нулевого размера**, что влияет на компоновку рамки узла вокруг него. Если в игре
`setImageResolver`/`inlineImages`, а resolver промахивается, генератор переходит к
передаче исходного `src` как есть, а не встраивает — `href` всё равно записывается,
просто он не разрешится, если что-то другое на странице не сможет его загрузить. Что
входит и что не входит в рамки обработки изображений/растра в целом, см. в разделе
[Известные расхождения](/ru/divergences).
