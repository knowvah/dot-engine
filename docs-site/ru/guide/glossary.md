# Глоссарий

По одному определению на термин, в алфавитном порядке английских терминов (порядок
заголовков сохранён таким же, как в английской версии). Каждое определение ведёт на
страницу руководства (или в исходный код), где термин разобран подробно.

## Кластер

Подграф, имя которого начинается с `cluster` (например, `subgraph cluster_build`), —
Graphviz рисует его как отдельную рамку, группирующую входящие в него узлы. Внутри
снимок геометрии @knowvah/dot-engine переименовывает каждый подграф-кластер в позиционное
имя вроде `cluster6` (`ClusterGeometry.name`), а не в имя из исходного DOT, поэтому
потребитель, которому нужно исходное имя, перед компоновкой строит карту `idByName`, а
после неё переименовывает ключи `snapshot.clusters`. Шаблон переименования см. в разделе
[Рецепты](/ru/guide/recipes), а создание кластеров через `addSubgraph` — в разделе
[Построение графа](/ru/guide/build-a-graph).

## Соответствие

Механически проверяемое свойство, на котором держится утверждение, что результат
рендеринга @knowvah/dot-engine «совпадает» с оракулом на C. После разбора обоих SVG в
нормализованные деревья элементов каждое числовое значение (координаты, данные пути,
`points`) должно совпадать в пределах фиксированного допуска — **±0,01pt** для
детерминированных механизмов (`dot`, `circo`, `twopi`, `osage`, `patchwork`) и
**±0,5pt** для итеративных силовых механизмов (`neato`, `fdp`, `sfdp`), — а каждое
нечисловое значение (теги, цвета, текст) должно быть в точности равным. Это не
утверждение о побайтовом совпадении вывода SVG. См. [Соответствие](/ru/conformance).

## Система координат / ось y

Нативная система координат Graphviz направлена **вверх по оси y**, начало — в нижнем
левом углу; браузеры и экраны направлены **вниз по оси y**, начало — в верхнем левом
углу. `getLayout` по умолчанию использует `yAxis: 'down'` (переворачивая каждую
координату y и нормализуя `bounds` к `(0, 0)`) и принимает `yAxis: 'up'`, чтобы вернуть
нативные координаты Graphviz без изменений. Операции рисования xdot (из `getDrawOps`)
всегда находятся в нативной системе с осью y вверх. См.
[Чтение вычисленной геометрии](/ru/guide/geometry).

## Расхождение

Отличие результата рендеринга @knowvah/dot-engine от оракула, которое исследовано,
для которого найдена первопричина и которое внесено в каталог, — в отличие от
отличий, молча терпимых. Каталогизированные расхождения относятся к одному из трёх
классов: принятые дельты (сознательно не приведённые в соответствие, например
недетерминизм чисел с плавающей запятой между платформами), отслеживаемый «длинный
хвост», который ещё устраняется, и явные не-цели. Отличие, не внесённое в список,
считается дефектом, а не принятым поведением. См. [Известные расхождения](/ru/divergences).

## DOT

Язык описания графов — `digraph { ... }` / `graph { ... }` с операторами узлов, рёбер и
атрибутов, — который @knowvah/dot-engine разбирает, прежде чем передать результат
механизму компоновки. См. [Начало работы](/ru/guide/getting-started).

## Определитель размера / резолвер изображений

Две внедряемые точки расширения для внешних изображений (узлы usershape и ячейки
`<IMG>` в HTML-метках). `ImageSizer` сообщает естественную ширину и высоту
изображения, чтобы расчёт размеров узлов и компоновка меток могли идти без загрузки
пикселей; `ImageResolver` предоставляет фактические байты изображения для встраивания
во время рендеринга. См. [Изображения](/ru/guide/images).

## Механизм компоновки

Один из восьми алгоритмов компоновки, которые регистрирует @knowvah/dot-engine,
выбираемый по имени (`renderSvg(dot, engine)`): `dot` (иерархическая/послойная),
`neato` (пружинная модель, Камада — Кавай), `fdp` (силовая), `sfdp` (многомасштабная
силовая, для больших графов), `circo` (круговая), `twopi` (радиальная), `osage`
(кластерная) и `patchwork` (квадратная древовидная карта). См.
[Механизмы компоновки](/ru/guide/engines).

## Оракул

Нативный бинарник `dot` Graphviz на C, собранный из канонического исходного кода на C,
с которым сверяется каждый результат рендеринга @knowvah/dot-engine. @knowvah/dot-engine
запускает этот бинарник напрямую (никогда не сборку на WASM), чтобы избежать дрейфа
ABI между эталоном и портом. О том, как выполняются и отражаются в отчётах сравнения с
оракулом, см. [Соответствие](/ru/conformance) и [Паритет](/parity).

## Ранг / rankdir

В иерархической компоновке `dot` **ранг** — это слой узлов, расположенных на одной
глубине на рисунке. `rankdir` задаёт направление, в котором идут ранги, — по умолчанию
`TB` (сверху вниз) либо `LR`, `BT`, `RL`; задаётся как атрибут графа
(`b.setAttr('rankdir', 'LR')`). См. [Построение графа](/ru/guide/build-a-graph).

## Сплайн / трассировка рёбер

Криволинейный (кривая Безье) путь, по которому рисуется ребро; вычисляется кодом
трассировки, который огибает препятствия — узлы и кластеры. @knowvah/dot-engine
предоставляет маршрутизированные контрольные точки как `EdgeGeometry.points` —
упорядоченный массив точек `{x, y}` в пунктах — из `getLayout`. См.
[Чтение вычисленной геометрии](/ru/guide/geometry).

## Измеритель текста

Внедряемая точка расширения (`TextMeasurer`), которая сообщает ширину и высоту меток,
чтобы расчёт размеров узлов и меток рёбер мог идти до компоновки. @knowvah/dot-engine
автоматически подбирает один на каждый рендеринг — сначала явный `setTextMeasurer`, затем
`<canvas>` браузера, если он доступен, затем встроенный детерминированный
`EstimateTextMeasurer` в Node — либо принимает собственную реализацию. См.
[Измерение текста](/ru/guide/text-measurement).

## Usershape

Термин Graphviz для узла, форма которого — это внешне заданное изображение (через
атрибут `image`), а не нарисованный многоугольник или эллипс. @knowvah/dot-engine
разрешает usershape через внедряемую точку расширения определителя размера/резолвера
изображений, а не читает файлы напрямую, благодаря чему библиотека остаётся безопасной
для браузера. См. [Изображения](/ru/guide/images).

## xdot

Расширенный формат операций рисования DOT: структурированный поток операций (задать
цвет заливки/обводки, задать шрифт, залить/обвести эллипс или многоугольник, нарисовать
кривую Безье, вывести текст), в точности описывающий, как следует нарисовать
отрисованный граф, в порядке рисования. `getDrawOps` возвращает этот поток в виде
типизированных значений `XdotOp` — для управления собственным средством отрисовки
(canvas, WebGL, PDF) без разбора SVG. См.
[Собственный рендеринг с xdot](/ru/guide/xdot-drawops).
